不具合を調べて直す。症状: $ARGUMENTS

原則: **根本原因を確かめるまで直さない**。推測の修正を重ねない（1 回の変更で試すのは 1 つの仮説）。症状の出た場所ではなく、最初に間違った場所を直す。

## 1. 再現する（最初に必ず）

- 失敗を**単独のコマンド 1 つ**で再現できる形にする。できれば落ちるテストにする（そのまま回帰テストになる）
- エラーメッセージとスタックトレースを最後まで読む。ビルド・型エラーは最初のエラーから（後続は連鎖のことが多い）
- 実行は速く・短く: 対象のテストだけ（`-k`・ファイル指定）、最初の失敗で止める（`-x`）、出力は静かに（`-q`）
- 再現しない・ときどき落ちる → 下の「不安定な失敗」

## 2. 範囲を絞る（安い順に。原因が見えたらそこで 3 へ進み、残りの手段は使わない）

1. **スタックトレースが指す箇所を読む**: 例外を出した関数と、その値を渡した呼び出し元。多くはここで分かる
2. **逆向きの追跡**: 壊れた値がどこで作られたかを、呼び出し元へ遡る
3. **最近の変更**: `git log --oneline -15 -- <関係するパス>`、`git diff`
4. **動く例との比較**: 同じコードベースで動いている似た箇所（同じ API の別の呼び出し、似たテスト）を読み、違いを全部挙げる
5. **境界での計測**: 層をまたぐなら、各層の入口と出口で値を出し（ログ・print・assert）、1 回の実行でどこで壊れるかを特定する。計測は後で消す
6. **git bisect**: 以前は動いていて、上で原因が見えないとき（作業ツリーがきれいで、原因がコミット済みの履歴にあるときだけ）。`git bisect start <悪い版> <良い版> && git bisect run <再現コマンド>`（再現コマンドは古い版にも無いファイルに依存しない形で。終わったら `git bisect reset`）

## 3. 仮説を立てて反証する

- 仮説を書く（「X が Y なので Z になる」）。多くて 3 つ、確からしい順に。原因がはっきり見えているなら、仮説 1 つと、それを確かめる実験 1 つでよい
- それぞれに「どうなれば外れと分かるか」の実験を決め、安い順に 1 つずつ試す。1 回に変えるのは 1 つだけ
- 読む量が多く、互いに独立な仮説は、Explore サブエージェントで並列に調べる（1 仮説 1 エージェント。「支持／否定」と根拠の path:line を 5 行以内で返させる）。大量のコードをメインの会話に読み込まない
- 独立した複数の失敗（別のテストファイル・別のサブシステム）は、失敗ごとに並列で調べる。原因が共通しそうなら、まず 1 つを調べる

## 4. 直す

1. 再現コマンドを回帰テストにし、落ちることを確かめる（RED）
2. 根本原因を直す。共有の関数が原因なら、その関数で 1 回直す（呼び出し元を grep で全部確かめる。症状の出た経路だけを塞がない）。そのうえで、不正な値が入ってきた境界（外部入力の受け口、層の入口）で検証を足すと安く防げるなら足す（多層の防御。根本原因の修正の代わりにはしない）
3. 回帰テストが通る（GREEN）→ `/accept`（元の症状が再現しないことを、成果物を動かして確かめる）→ `/verify`（関係するテスト → 全体）
4. 計測のために足したログ・print・一時ファイルを消す

## 5. 直らないとき

修正を 3 回試して直らない、または直すたびに別の場所が壊れるなら、止める。個別の症状ではなく設計・前提を疑う。分かったこと・試したこと・次の仮説を Linear（無ければ報告）に書き、ユーザーに相談する

根本原因がコードの外にある（外部サービスの障害、環境・権限、壊れた入力データ、依存の不具合）と分かったときは、コードで症状を隠さない。証拠（再現の手順・観測した値）を添えて報告し、こちらでできる対処（入力の検証で分かりやすく失敗させる、再試行、依存の版の固定）はユーザーと決める

## 報告（5 行以内。1 項目 1 行）

```
根本原因: <1 文> path:line
証拠: <何で確かめたか（bisect の結果、計測の値など）>
修正: <どこをどう直したか>
回帰テスト: <テスト名>（RED を確認済み）
検証: <コマンド> → <結果>
```

## 種類別の要点

- **ハーネス自体の不具合**（関門が想定外に止める・通す、証拠が記録されない）: `~/.local/state/harness/log`（hook の 1 呼び出し 1 行。Bash で開くと迂回の語の検出に掛かるので Read ツールで読む）、git dir の `harness-last-accept`・`harness-last-review`・`harness-red-log`、要件の写し（`harness-hook requirements-path`）を見て、どの証拠が欠けたか・どの hook が何を記録したかを突き合わせる

- **不安定な失敗**: 繰り返し実行で頻度を測る（例 `for i in $(seq 20); do <コマンド> || echo FAIL; done`）。順序依存・共有状態（グローバル変数、一時ファイル、時刻、乱数の種、並列実行）を疑う
  - 汚染するテストの特定: 落ちるテストだけなら通り、全体だと落ちるなら、手前で走るテストの一覧を半分ずつにして「前半 + 落ちるテスト」を実行し、落ちる側へ絞っていく（二分探索。pytest なら順序を固定し `pytest <テストの一覧> <落ちるテスト>`）
  - タイミング: 固定の sleep で待たず、条件が満たされるまで短い間隔で確かめ、上限の時間で失敗させる形にする（例: 「ファイルができる・ポートが開く・状態が変わる」まで 50ms ごとに確かめ、5 秒で打ち切る）
- **ビルド・型エラー**: 1 種類ずつ、最小の差分で直す。型を any にする、チェックを外す、テストを消す、で通さない。依存の版の食い違いは lockfile と実際に入っている版を確かめる
- **環境による違い（手元では動く）**: 違いを列挙して（言語・依存の版、環境変数、OS、パス、権限、ネットワーク、キャッシュ）1 つずつ潰す
- **性能**: 推測で最適化しない。計測（プロファイラ・時間）で場所を特定してから直し、直した後も計測する
- **「ありえない」値**: まず前提を確かめる（入力、設定、実際に動いているコードの版、ビルドの成果物やキャッシュが古くないか）

## やってはいけない

原因が分からないまま修正を書く／複数の変更を一度に入れる／テストを弱めて通す／例外を握りつぶして黙らせる／「たぶん直った」で報告する
