コード変更を敵対的にレビューする。引数: $ARGUMENTS

モードは引数の**最初の語だけ**で決める（本文に出てくる語では決めない）: `fix` → 範囲限定の再レビュー、`branch` → ブランチ全体、それ以外 → フル。

共通:
- 最初に `sh ~/.claude/skills/review/snapshot.sh` で今の版（作業ツリー全体の tree ID）を取り、出力の先頭に「レビューした版: <ID>」と書く。次の `/review fix` が修正差分の起点に使う。取れなければ「レビューした版: 取得失敗（理由）」と書いてレビューは続ける（次の fix はフルになる）
- 検証コマンドと結果は依頼に書かれている。回し直さない（実行の方針はシステムプロンプト）
- 仕様適合の基準は、承認済みの要件と受け入れ条件の写し（`cat "$(harness-hook requirements-path)"`）。依頼の文面ではなくこちらを正とする。無い・空なら、照らし合わせる基準が無いので仕様適合は「修正が必要」
- 受け入れ検証の報告は hook が `"$(git rev-parse --absolute-git-dir)/harness-last-accept"` に保存している。読んで、全条件が合格か、残された検査スクリプトが条件を本当に確かめているか（成果物を実際に実行しているか、assert が条件の性質に対応しているか、サンプルの入力が境界を含むか）を見る。報告の鮮度は hook が指紋で確かめるので、報告の版は見なくてよい
- テストが先に落ちたこと（RED）は、hook が記録した `"$(git rev-parse --absolute-git-dir)/harness-red-log"`（失敗したテストのコマンドと出力。implementer の分も入る）で確かめる。依頼に貼られた出力より、こちらを正とする
- 対象の差分が空なら、「レビューした版」の行と「レビュー対象の変更がない」だけを書く（判定行は書かない）

## フル（最初の 1 回）

1. 対象: 作業中の差分（`git status --porcelain --untracked-files=all`、`git diff HEAD`、未追跡ファイルは Read）
2. 変更した関数・クラスの呼び出し元と、同じ役割の既存コードを `Grep` で探して読む
3. テストファイルを読み、何を検証していて何を検証していないかを確かめる
4. 軸 1〜3・報告前の関門・重大度に従って、フルの出力形式で返す（指摘の番号は `R1-<n>`）

## fix（範囲限定の再レビュー）

依頼に書かれているもの: 回数（2 か 3。ユーザーの裁定後の 1 回は 4）、直したこと、ユーザーの裁定（あれば）、検証コマンドと結果。
前回の報告は hook が `"$(git rev-parse --absolute-git-dir)/harness-last-review"` に保存している。前回の版と未解決の重大・中の指摘はそこから読む（依頼の転記と食い違えば、保存された方を正とする。無ければ依頼の記述を使い、その旨を出力の先頭に書く）。
これは新しいフルレビューではない。見るのは「指摘が直ったか」と「修正が新しく壊したもの」だけ。

1. 前回の版を `git cat-file -t <ID>` で確かめる。tree でなければフルの手順に切り替え、出力の先頭にその旨を書く
2. 今の版を取り、`git diff --stat <前回> <今>` と `git diff <前回> <今>` を読む。これが修正差分
3. 指摘ごとに「直った／直っていない」を根拠（path:line）つきで判定する。依頼に反論（その指摘が誤りである根拠）があれば、コードで確かめ、正しければ「取り下げ」（判定の対象外）、誤りなら「直っていない」とする。基準は「指摘が述べた失敗が、修正差分によって解消されたか」（直した場所が指摘の行と違ってもよい。例: テストを別のファイルに足した、呼ばれる側で直した）。修正差分が空なら「直っていない」。「直そうとした」は直ったではない
4. 修正差分について、変更した関数の呼び出し元を読み、軸 1〜3 を当てる（修正のテストがあるか、テストを弱めていないか）。修正が原因の破損は、未変更の呼び出し元やテストで起きても「修正による新しい問題」
5. 修正差分に触れていない箇所で気づいたことは「範囲外」に書く（判定に影響しない。ただし重大なら判定に含める）。フルレビューで見た箇所を見直さない
6. ユーザーが見送りと裁定した指摘は「ユーザー判断で見送り」に書き、判定の対象外にする
7. 範囲限定の出力形式で返す（新しい指摘の番号は起点と同じ接頭辞で `R<回数>-<n>` か `B<回数>-<n>`）

## branch（ブランチ全体）

1. 対象: `git diff $(git merge-base main HEAD 2>/dev/null || git merge-base master HEAD)...HEAD` と、あれば作業中の差分
2. 個々の行より、**全体の一貫性・構造の劣化・重複・命名のぶれ**を優先して見る
3. フルの出力形式で返す（指摘の番号は `B1-<n>`）
