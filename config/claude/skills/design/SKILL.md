設計を合意する。対象: $ARGUMENTS

目的: 作り始めてから「思っていたのと違う」「別のやり方がよかった」とならないようにする。**設計を合意するまで本番のコードを書かない**（確かめるための小さな試作は一時ディレクトリで行い、捨てる）。

## 1. 文脈を把握する

- 関係するコード、既存の似た仕組み、制約（依存・規約・テストの仕組み）は Explore サブエージェントに調べさせ、20 行以内の要約で受け取る（「どこに何があり、何を再利用でき、どこに触ると危ないか」）。メインの会話に大量のコードを読み込まない
- 作らずに済まないかを最初に確かめる（作らない → 既存のコード → 標準ライブラリ → 既存の依存 → 最小のコード）

## 2. 要件を確かめる

- 分からないこと・複数に解釈できることを洗い出し、AskUserQuestion でまとめて聞く（1 回に 4 問まで。各問に選択肢と推奨を付ける。答えで次の問いが変わるときだけ、回を分ける）
- 目的（なぜ要るか）、利用者、成功の基準、対象外、制約（性能・互換性・期限）を確かめる
- 受け入れ条件を、成果物を動かして確かめられる性質で書けるところまで詰める（書き方は `/issue` の手順 4）。書けないなら、要件がまだ曖昧だということ

## 3. 案を比べる

- 2〜3 案を出す（本当に 1 案しかないなら、そう書いて理由を添える）。各案: 概要 2〜3 行、利点、欠点とリスク、手間、将来の変更への強さ
- 推奨を 1 つ選び、理由を書く。好みで分かれる点はユーザーに選んでもらう

## 4. 設計を書く（推奨案で。要る節だけ、短く）

- 構成（部品と責務）、データの流れ、インタフェース（関数・API・ファイルやデータの形式）、エラーと境界の扱い
- テストと受け入れの方針（どの受け入れ条件を、どのテストと `/accept` の検査で確かめるか）
- 移行・互換性（既存のデータや利用者への影響）
- 対象外（今回は作らないもの。要求されていない拡張性・設定・抽象化を足さない）
- 図が効くなら文字の図を 1 つ

## 5. 合意して保存する

- 示す前に自分で点検する（4 項目）: **空欄**（決めていない所・「TBD」が無いか）、**矛盾**（要件・受け入れ条件・設計の節どうしが食い違っていないか）、**曖昧さ**（2 通りに読める文が無いか）、**範囲**（要件に無いものを足していないか、要件の一部を落としていないか）
- 独立した部分が複数ある大きな依頼なら、部分ごとに子 issue に分け、それぞれで設計と受け入れ条件を合意する（1 つの設計に詰め込まない）
- 設計をユーザーに示して承認を得る。直しがあれば 3〜4 に戻る
- issue の本文に `## 設計` として保存し、`## 要件（合意）` と `## 受け入れ条件` も最新にする（コメントではなく本文）
- 長く残るアーキテクチャの判断は、リポジトリの設計メモ（README か docs/）にも短く残す（理由は issue 番号で指す）

## 6. 次へ

L は plan mode で計画を作る（`/implement` の形）。M は実装へ（`/tdd`）。

## やってはいけない

設計の合意の前に本番のコードを書く／1 案だけ示して選ばせたことにする／聞けば分かることを推測で決める／要求されていない拡張性を足す／受け入れ条件を「正しく動く」のような確かめられない形のまま進む
