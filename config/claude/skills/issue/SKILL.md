Linear の issue $issue を起点に作業する。

1. 読む: `get_issue`（関連・親子も含む）とコメント。既存の決定事項があれば従う
2. 着手を記録: 状態を In Progress、担当を me にする
3. 要件を固める: 不明点・複数に解釈できる点・前提をすべて洗い出し、AskUserQuestion でまとめて質問する。**完全に理解するまで設計・実装に入らない**
4. issue の**本文**に書く（`save_issue` の patch で追記。コメントではない）:
   - `## 要件（合意）`: ユーザーの言葉をなるべくそのまま
   - `## 受け入れ条件`: 成果物を**実際に動かして確かめられる性質**で、1 行ずつ `AC1:` `AC2:` … の番号を付けて書く（「入力・操作 → 期待する結果」と確かめ方）。`/accept` の acceptor はこの番号で確かめ、hook は要件の写しの番号がすべて報告で合格しているかを突き合わせる（番号が無いと受け入れ済みにならない）
     - データ: 件数、列と型、必須の値の欠け、値の範囲・形式、一意性、参照の整合、集計値、再現性（乱数の種）、境界（空・最大・重複や欠損のある入力）
     - CLI・スクリプト: 出力、終了コード、作るファイル、異常な入力、2 回実行したとき
     - API・ライブラリ: 応答の形と値、エラー。画面: 操作の手順と、表示・状態
     - 本物の入力の場所（無理なら本番に近いサンプルを用意すること）と、成果物の動かし方
     - 「正しく動く」「要件を満たす」のような確かめられない書き方はしない
   - 設計判断や作り方の候補が複数あれば `/design` で 2〜3 案を比べて合意し、`## 設計` も本文に保存する
   - L は plan mode で計画を作り、`## 計画` も本文に保存する（`/implement` の形）
5. 規模を判定（CLAUDE.md の S/M/L。迷ったら重い方）し、M / L は 4 の内容を示して**ユーザーの承認を得てから**実装に入る
6. 承認された `## 要件（合意）` と `## 受け入れ条件`（あれば `## 設計`）を、そのまま `harness-hook requirements-save <<'EOF' … EOF` で保存する（作業ブランチを切った後に。ブランチごとのファイル。git dir の下なので Write ツールでは書けない）。acceptor と reviewer はここを読み、hook はこの内容を証拠の指紋に含める。要件が変わったら issue の本文とこのファイルの両方を直す
7. コメントは節目だけ（方針変更、詰まった点、途中で止めるときの状態と次の手順）。要件や計画が変わったら本文を直す
8. 完了時: M / L は `/wrap-up` のコメントで兼ねる。S はコメント 1 つ（やったこと／検証／残件）。状態は CLAUDE.md の Linear の節に従う（Done は統合の後、確認してから）

補足: $ARGUMENTS
