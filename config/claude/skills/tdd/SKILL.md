**鉄則**: 振る舞いを変える本番のコードは、それを確かめる落ちるテストより先に書かない。先に書いてしまったら、それを消してテストから書き直す（後から書いたテストは実装をなぞるだけになる）。

## 1 周の手順

1. **RED**: 振る舞いを 1 つだけ確かめるテストを書き、実行して落ちるのを見る
   - **期待した理由で落ちること**: 未実装の振る舞いを確かめる assert の失敗であること。import エラー・名前の typo・構文エラーで落ちるのは RED ではない（何も確かめていない）。関数がまだ無ければ、先に空の関数（仮の値を返す）を作り、assert で落ちる状態にする
   - 失敗したテストの実行は、hook が git dir の `harness-red-log` にコマンドと出力を記録する（reviewer はそれで RED を確かめ、記録が無ければテスト軸を「修正が必要」にする）。自分でも失敗の 1 行を確かめておく
2. **GREEN**: テストを通す最小の実装を書く。テストを変えて通さない。関係するテストだけを実行して、通るのを見る
3. **REFACTOR**: テストが緑のまま、命名・重複・置き場所・残骸を整える（触った箇所は触る前より整った状態で終える）。整えたら再実行する
4. 次の振る舞いへ。すべて終わったら `/accept` → `/verify` → `/review`

## よいテスト

- 名前が振る舞いを表す（例:「空の入力なら 0 を返す」）。1 つのテストで確かめる振る舞いは 1 つ
- 利用者が使う形（公開されたインタフェース）を通して確かめる。内部の関数や private の状態を直接見ない
- 境界（空・1 件・最大・重複・欠損・不正な値）とエラーの経路を含める
- 速く、順序に依存せず、何度でも同じ結果になる（時刻・乱数・ネットワーク・ファイルは固定するか差し替える）
- バグの修正は、まず症状を再現するテストから（原因がすぐに分からなければ `/diagnose`）

## 避けるべき書き方（見つけたら直す。reviewer はテスト軸で「修正が必要」にする）

- モックの振る舞いを確かめている（本体を通らず、モックが呼ばれたことだけを見ている）
- 自分が持つコードをモックする。モックの戻り値が本物と食い違う（不完全なモック）。差し替えるのは外との境界（ネットワーク、時刻、外部サービス）だけ
- テストのためだけの本番のメソッド・フラグ（テストからしか呼ばれないもの）
- 固定の sleep で待つ（条件が満たされるのを待つ形にする）
- 常に通るテスト（assert が無い、例外を握りつぶす、期待値を実装と同じ計算で作る）
- スナップショットや期待値を、確かめずに今の出力で上書きする
- 既存のテストを弱めて通す（期待値を実装に合わせる、skip、削除）。hook もこれを関門の対象にしている

## 設定・依存の版だけの変更

振る舞いのコードを変えない設定や依存の版の変更（ツールの版上げ、lint の設定など）は、RED を作れない。その代わりに受け入れ条件（例:「新しい版で全体の検証が通る」「設定した警告が出る」）を書き、`/accept` と宣言した検証で確かめる。reviewer も RED を求めない。

## テストが書きにくいとき

設計の問題の合図。依存を引数で渡す、副作用（I/O）と計算を分ける、小さな関数に分ける。テストを諦めて実装だけを書かない。自動テストにできない振る舞い（画面の見た目など）は、受け入れ条件にして `/accept` で実際に動かして確かめる。

## 言い訳と、それへの答え

| 言い訳 | 答え |
|---|---|
| 小さな変更だからテストは要らない | 小さな変更ならテストも小さい。書く |
| 後でテストを書く | 後から書いたテストは実装をなぞる。先に書く |
| 手で動かして確かめた | 次の変更で壊れても気づけない。テストにする（手で確かめたいことは `/accept` が検査スクリプトとして残す） |
| テストを書くと遅くなる | 壊れたまま進んだ後に直す時間の方が長い |
| モックすれば速い | 本物の振る舞いを確かめていない。外との境界だけを差し替える |
| 振る舞いは変えていない（リファクタだ） | それなら既存のテストが守っているはず。守るテストが無ければ、先に今の振る舞いを固定するテストを書く |
